# Mac ↔ Windows 跨平台联调计划

> 本文由 Mac 侧发起。目的：把只能在双机环境暴露的问题找出来。
>
> **单机（同机双实例）已验证通过的部分不必重测**：文件传输吞吐、断点续传、
> 缓存命中、传输中被文字取代、配对自动发现、空闲占用。这些两端都是 Mac，
> 测不出跨平台差异。本计划只针对**两端行为可能不一致**的地方。
>
> 已排除的"伪风险"（查过代码，不必测）：
> - **字节序**：帧长度前缀用 `to_be_bytes`/`from_be_bytes` 显式大端，
>   且 x86_64 与 aarch64 都是小端，不存在端序问题。
> - **路径分隔符泄露**：`FileMeta.name` 只存文件名不含目录
>   （`meta_for_path` 取的是 `file_name()`），接收侧 `sanitize_name` 还会
>   再剥一次 `/` 和 `\`。我在 Mac 侧实测确认 `C:\Users\x\evil.txt` →
>   `evil.txt`、`../../etc/passwd` → `passwd`，不会越界写文件。

---

## 0. 双方约定

| | Mac 侧 | Windows 侧 |
|---|---|---|
| 分支 | `macos-platform-impl` | 同左（`git pull` 后 checkout） |
| 构建 | `cargo build --release` | `cargo build --release` |
| 日志 | `CLIPSYNC_LOG=debug` | `CLIPSYNC_LOG=debug` |

⚠️ **必须用 release/fast 构建**。debug 下同一传输慢 15 倍，会把性能问题的
判断带偏。

⚠️ **`max_bytes` 默认 100 MiB**，超限内容被静默跳过（`TooLarge` 只在 DEBUG
打日志）。测试文件请控制在 100 MiB 以内，否则会看到"两边都没反应"却找不到
原因——我在 Mac 侧用 400MB 文件测试时就踩过这个坑。

> **此条已过时**（当时的记录留在这儿）。这个设置后来改名 `auto_fetch_bytes`
> 并挪到了**接收侧**：超限的文件不再被跳过，而是挂在接收方的托盘上等人点
> 「取回」。测试大文件不必再迁就上限了。

## 1. 配对（第一步，Windows 侧先做）

Mac 侧会在推送后启动主持方并把配对码发给你。届时你只需：

```powershell
# 同一局域网内，不需要 IP
clipsync pair <配对码>

# 若不在同一局域网，Mac 侧会同时给出可用地址
clipsync pair <Mac的IP> <配对码>
```

**期望**：双方都打印 `✓ 配对成功` 并列出对方地址；之后各自 `clipsync list`
能看到对方。

配对码是**一次性**的，且经 SPAKE2 保护，短期内可公开传递；若过期或连不上，
让 Mac 侧重新 `pair --host` 生成新码即可。

## 2. Windows 侧要跑的测试

每项都请记录：**实际现象 + 相关日志行**。失败的项目尤其要贴日志。

### T1 文本往返（基线，确认链路通）

1. Windows 复制一段纯 ASCII 文字 → Mac 应出现
2. Windows 复制一段中文 + emoji（如 `测试🎉内容`）→ Mac 应出现且**不乱码**
3. Mac 侧会同样发一段过来，确认 Windows 收到且不乱码

> 关注点：UTF-8 在两端的往返。这一项若失败，后面的都不用测了。

### T2 文件名编码（**最可能出问题的一项**）

在 Windows 上准备这几个文件（内容随便，几十字节即可）：

```
ascii.txt
中文文件名.txt
带 空格 的文件.txt
café.txt              ← 带重音符，用来试 Unicode 规范化
测试🎉emoji.txt
```

逐个（或一次全选）在资源管理器里复制 → 在 Mac 的 Finder 里粘贴。

**请记录每个文件**：
- 粘贴出来的文件名是否与源**逐字一致**（特别是 `café`：是 `é` 一个字符，
  还是 `e` + 组合重音两个字符）
- 文件内容是否一致

> **为什么单测这一项**：文件名以 `String` 走 postcard 编码，两端都是 UTF-8，
> 理论上没问题。但 macOS 历史上 HFS+ 会把文件名强制转成 NFD（`é` 拆成两个
> 码位），APFS 虽然保留 NFC（我在 Mac 侧实测确认了这一点），Windows/NTFS 则
> 一律按 NFC 存。所以 **Mac→Win 方向**可能出现文件名"看起来一样但字节不同"，
> 进而影响下面 T4 的缓存命中。

### T3 Windows 保留字符与路径分隔符

Mac 侧会发送一个名为 `a:b?c*d.txt` 的文件（这些字符在 Windows 文件名里非法）。

**期望**：Windows 侧接收后落地为 `a_b_c_d.txt`（非法字符被替换成 `_`），
**不报错、不崩溃**。接收侧有 `sanitize_name` 做这件事，这一项就是验证它。

> Mac 侧已实测该函数的行为（它目前没有单元测试覆盖，我是单独跑出来的）：
> `a:b?c*d.txt` → `a_b_c_d.txt`，`C:\Users\x\evil.txt` → `evil.txt`，
> `../../etc/passwd` → `passwd`，空名 → `unnamed`；中文/emoji/空格原样保留。
> 所以 T3 要确认的其实是**真实落盘时 Windows 是否接受**这个结果，
> 而不是函数逻辑本身。

反过来，Windows 侧请发一个名为 `normal.txt` 的文件即可（Windows 不允许创建
含 `:` 的文件名，无法构造反向用例）。

### T4 跨平台缓存命中与断点续传（**第二个高风险项**）

1. Windows 复制一个 50MB 左右的文件 → 等 Mac 接收完成
2. **再复制同一个文件**（不做任何修改）→ 观察 Mac 侧日志

**期望**：Mac 侧出现 `文件已在缓存中命中，秒同步（零传输）`。

**若没有命中**，请贴出两次传输时双方日志里的文件 `id`（DEBUG 级别可见）。

> **为什么这里高风险**：缓存键 `id` 由 `(文件名, 大小, 修改时间纳秒)` 派生。
> NTFS 的时间戳精度是 100ns 刻度，APFS 是 1ns；且两端读到的 mtime 是否
> 完全相同并无保证。若 `id` 两端算不出同一个值，缓存命中和断点续传都会失效
> ——但表现只是"每次都重传"，不会报错，**很容易被忽略**。

3. 断点续传：Windows 复制一个 90MB 文件，传输进行到一半时**立刻复制一段
   文字**。期望 Mac 侧文字立即出现、文件传输中止并提示"已收部分保留待续传"。
   随后再复制该文件，期望日志出现"断点续传"，完成后 **MD5 与源一致**
   （`certutil -hashfile <文件> MD5`）。

### T5 敏感内容（Windows → Mac 方向）

用密码管理器（KeePass/1Password 等）复制一个密码。

**期望**：Windows 侧日志出现 `本地变化跳过 (Sensitive)`，**Mac 侧收不到任何东西**。

> Mac 侧的反向验证（Mac 复制密码 → Windows 收不到）我已在本机确认：日志为
> `本地变化跳过 (Sensitive)`。这里要验的是 Windows 侧的标记检测在真实密码
> 管理器下是否也生效。

### T6 图片（Windows → Mac 方向）

1. Windows 截图（`Win+Shift+S`）后复制 → Mac 应能粘贴出图片
2. Mac 侧会发一张截图过来，确认 Windows 能粘贴

> ⚠️ **已知缺口**：Mac 侧若图片是 **16-bit 浮点 TIFF**（Retina 屏上用
> `NSImage.lockFocus` 生成的那类），`arboard` 解码失败，Mac→Win 方向该图片
> 传不过去，日志为 `读取剪贴板图片失败: ... could not be converted`。
> 8-bit 图片（含截图、P3 宽色域）一切正常。详见 `docs/MACOS.md` 第 3 节。
> 若你在 Win 侧没收到 Mac 的某张图，**先看 Mac 侧日志是不是这个错**，
> 不要误当成网络问题。

### T7 长连接稳定性

两端都保持运行 15 分钟以上，期间偶尔复制点东西。

**期望**：连接不断、CPU 接近 0、内存不增长。请记录 15 分钟前后的
CPU 时间与内存（任务管理器即可）。

## 5. 出问题时

- 编译报错或 API 对不上：贴完整报错。
- 连不上：先确认防火墙（Mac 首次监听会弹窗要点允许；Windows 同理），
  再用 `clipsync addrs` 对比两边地址是否在同一网段。
- 收不到内容但连接正常：开 `CLIPSYNC_LOG=debug`，找 `本地变化跳过 (...)`
  这行，括号里的原因（`Sensitive` / `TooLarge` / `Echo` / `KindDisabled`）
  直接说明了被跳过的理由。
