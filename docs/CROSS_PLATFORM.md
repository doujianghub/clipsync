## Mac 侧结果

### ✅ T1 文本往返

| 方向 | 内容 | 结果 |
|---|---|---|
| Mac → Win | `MAC-T1-ascii-hello` | 已发出，18 字节 |
| Mac → Win | `MAC-T1-中文测试🎉emoji` | 已发出，28 字节（与 UTF-8 编码长度吻合） |
| Win → Mac | Windows 侧发来的文本 | ✅ 已应用，无乱码 |

### ✅ T2 文件名编码 —— **未发生 NFD 转换，逐字节一致**

Windows → Mac 方向收到 5 个文件，落地文件名的 UTF-8 字节：

| 文件名 | 收到的 hex | 规范化形态 | 内容 |
|---|---|---|---|
| `ascii.txt` | `61736369692e747874` | NFC | `ascii content` |
| `café.txt` | `636166**c3a9**2e747874` | **NFC** | `cafe accent content` |
| `中文文件名.txt` | `e4b8ade69687e69687e4bbb6e5908d2e747874` | NFC | `chinese name content` |
| `带 空格 的文件.txt` | `e5b8a620e7a9bae6a0bc20e79a84e69687e4bbb62e747874` | NFC | `spaces content` |
| `测试🎉emoji.txt` | `e6b58be8af95**f09f8e89**656d6f6a692e747874` | NFC | `emoji content` |

**关键结论**：`café.txt` 收到的是 `c3a9`（é 单码位，NFC），与 Mac 本地创建的
同名文件字节**完全相同**。计划中担心的 "HFS+ NFD 转换" 未出现——现代 APFS
保留 NFC，这条风险实际不成立。emoji 的 4 字节序列 `f09f8e89` 也完整无损。

文件已正确进入剪贴板，Finder 中可直接粘贴出全部 5 个文件。

### ✅ T3 Windows 保留字符

- Mac → Win：已发送 `a:b?c*d.txt`（macOS 允许这些字符）。
  **需 Windows 侧确认**落地为 `a_b_c_d.txt` 且不报错。
- Win → Mac：Windows 无法创建含 `:` 的文件名，故无反向用例，符合预期
  （对方发来的 5 个文件中确实没有该文件）。

### ✅ T4 跨平台缓存命中与断点续传 —— **两项高风险均通过**

**缓存命中（本次联调最值得关注的结果）**：

```
05:42:08  已同步 [文件] 52428800 字节 → 1 台设备      ← Mac 发出 50MB
05:42:20  文件已在缓存中命中，秒同步（52428800 字节，零传输）
```

计划中担心的 **NTFS(100ns) 与 APFS(1ns) 时间戳精度差异导致 `id` 算不出同一
值**，实测**没有**发生——跨平台缓存命中正常，`id` 两端一致。

**断点续传（Windows 侧发起，Mac 侧接收）**：

```
05:46:04  开始接收 1 个文件（共 94371840 字节）
05:48:04  开始接收 1 个文件（共 94371840 字节，已有 14680064 字节，断点续传）
05:48:09  已接收 1 个文件并放入剪贴板
```

从 14,680,064 字节处正确续传。落地文件：

- `t4_90mb.bin`，大小 `94371840`
- **MD5 = `a1abfee8e3bacbb69be992bc8a648e59`**
- ⚠️ **请 Windows 侧比对源文件 MD5 是否一致**（`certutil -hashfile t4_90mb.bin MD5`）

### ✅ T5 敏感内容（Mac → Win）

用带 `org.nspasteboard.ConcealedType` 标记的剪贴板内容测试：

```
05:58:23  DEBUG 本地变化跳过 (Sensitive)
```

Mac 侧正确拦截，**未发出**。请 Windows 侧确认**没有**收到该内容。

> 说明：Mac 侧是用 Swift 脚本模拟密码管理器的标记。真实密码管理器
> （1Password/KeePassXC）是否也打这个标记，Mac 侧尚未用真软件验证过。

### ✅ T6 图片（Mac → Win）

```
06:06:18  已同步 [图片] 120000 字节 → 1 台设备
```

200×150 的 **8-bit** RGBA 图片已发出，请 Windows 侧确认能粘贴且图像正确
（橙色底 + 左下角黑色方块）。

> ⚠️ 已知缺口：若 Mac 侧图片是 **16-bit 浮点 TIFF**（Retina 上
> `NSImage.lockFocus` 的产物），`arboard` 解码失败，该图传不过去，
> Mac 侧日志为 `读取剪贴板图片失败: ... could not be converted`。
> 本次特意用 8-bit 构造以规避。详见 `MACOS.md` 第 3 节。

### ⚠️ 连接稳定性 —— 观察到一次断开与自动重连

```
05:32:25  对端已连接: KPC
05:57:17  对端已断开: KPC          ← 断开
05:59:43  已认证并连接对端: KPC     ← 约 2.5 分钟后自动重连成功
```

断开期间发出的一张图片被记为 `已复制 [图片] 120000 字节，但暂无对端连接`
——内容没有丢失或报错，只是当时无人接收，重连后重发即正常送达。

**需 Windows 侧确认**：05:57 前后是否重启过程序 / 改过配置？若是，则属正常
测试节奏，自动重连按预期工作；若**不是**，则说明存在非预期断连，需要进一步
排查（这会影响验证清单第 10 项"长时间 0 次断开"的结论）。
