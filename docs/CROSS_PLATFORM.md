## T2 文件名编码：发现 NFC/NFD 差异 ⚠️

### Windows → Mac（我发出的源端字节）

| 文件名 | UTF-8 hex |
|---|---|
| `ascii.txt` | `61736369692e747874` |
| `café.txt` | `636166`**`c3a9`**`2e747874` ← **NFC**，`é`=U+00E9 |
| `中文文件名.txt` | `e4b8ade69687e69687e4bbb6e5908d2e747874` |
| `带 空格 的文件.txt` | `e5b8a620e7a9bae6a0bc20e79a84e69687e4bbb62e747874` |
| `测试🎉emoji.txt` | `e6b58be8af95f09f8e89656d6f6a692e747874` |

发送日志：`05:36:33 已同步 [文件] 84 字节 → 1 台设备`（5 个文件）。

**需 Mac 确认**：收到的文件名 hex，特别是 `café.txt` 是 `c3a9`(NFC) 还是
`65cc81`(NFD)。

### Mac → Windows（我实际收到的字节）

| 收到的文件名 | UTF-8 hex | 与 Windows 源端对比 |
|---|---|---|
| `ascii.txt` | `61736369692e747874` | 一致 |
| `cafe´.txt` | `636166`**`65cc81`**`2e747874` | 🔴 **NFD**，与 NFC 源端**不一致** |
| `中文文件名.txt` | `e4b8ade69687e69687e4bbb6e5908d2e747874` | 一致 |
| `带 空格 的文件.txt` | `e5b8a620e7a9bae6a0bc20e79a84e69687e4bbb62e747874` | 一致 |
| `测试🎉emoji.txt` | `e6b58be8af95f09f8e89656d6f6a692e747874` | 一致 |
| `a_b_c_d.txt` | `615f625f635f642e747874` | T3，见下 |

**结论**：中文、emoji、空格全部逐字节一致；**只有带组合重音的字符出现
NFC/NFD 差异**——Windows 源端 `é` 是单码位 `c3a9`（9 字节文件名），从 Mac
收到的是 `e`+组合重音 `65cc81`（10 字节文件名）。

### 影响评估

1. **文件可正常落盘、内容无损**，肉眼看文件名也一样，所以不影响基本可用性。
2. **但会破坏跨平台缓存命中**：缓存键 `id = hash(文件名, 大小, mtime)`，
   文件名字节不同 → id 不同 → 同一个文件在两端算出两个 id，**每次都重传**，
   断点续传也无法跨方向复用。
3. 若把收到的文件再复制回去，会产生一个"看起来同名、实为不同字节"的条目。

### 待确认

我无法确定这是 **Mac 磁盘上文件名本身就是 NFD**，还是**传输路径中被转换**。
请 Mac 侧确认其源文件 `café.txt` 在磁盘上的字节：

```bash
ls | grep caf | xxd | head -2
# 或
python3 -c "import os;[print(f.encode('utf-8').hex()) for f in os.listdir('.') if 'caf' in f]"
```

- 若 Mac 磁盘上就是 `65cc81`：说明是文件创建时的规范化，属环境差异，
  可考虑在 `meta_for_path` 里对文件名做 NFC 归一化后再算 id。
- 若 Mac 磁盘上是 `c3a9`：说明我们的读取路径做了转换，需要查
  `filelist.rs` 的 macOS 实现。

**建议的修法**（待双方确认后再动）：在 `meta_for_path` 计算 `id` 时，对文件名
先做 NFC 归一化；文件名本身仍按原样传输与落盘。这样两端算出的 id 一致，
缓存命中恢复，且不改变用户看到的文件名。代价是引入一个 Unicode 规范化依赖
（如 `unicode-normalization`）。

## T5 敏感内容：发现真实泄漏缺陷，已修复 🔴→✅

### 现象

本机未安装密码管理器，故用密码管理器实际使用的标记
（`ExcludeClipboardContentFromMonitorProcessing`）模拟。**这是真实机制，
但未在真实密码管理器下验证过**，请知悉这一局限。

首次测试：密码文本被**同步了出去**，未被拦截。

### 排查

1. 查 `sensitive.rs` 的 diff → **Windows 分支未被改动**，排除本次合并引入。
2. 隔离测试（停掉守护进程排除自身干扰）→ 标记确实没设上。
3. 让设置方进程**保持存活**再测 → `06:04:52 本地变化跳过 (Sensitive)` ✅
   检测逻辑本身正常。
4. **关键观察**：该进程 8 秒后退出，随即
   `06:05:00 已同步 [文本] 23 字节` —— **同一条密码被同步了出去**。

### 根因（与平台无关，macOS 同样受影响）

1. 程序写入"密码 + 排除标记（空数据）"→ 我们正确判定敏感并跳过
2. **但 `Skip(Sensitive)` 分支不记录内容哈希**，引擎没记住这条内容
3. 该程序退出 → 系统 flush 剪贴板 → **空数据的自定义格式被丢弃，文本仍在**
4. 剪贴板序列号变化 → 监听器重读 → 看到"无标记的密码" → 判为新内容 → **广播**

即：**任何密码管理器在清理/退出/flush 后，先前受保护的密码都可能泄漏到
所有已配对设备。**

### 修复

`SyncEngine` 增加 `sensitive_hashes`（容量 64 的有界集合）：一旦判定敏感就
按内容哈希记住，**即便标记后来消失也继续跳过**。

新增两个回归测试：
- `sensitive_content_stays_blocked_after_marker_disappears`
- `sensitive_memory_is_bounded`

### 验证

实机复现原泄漏场景（设标记 → 进程退出 flush）：

```
06:31:27 本地变化跳过 (Sensitive)   ← 标记存在
06:31:33 本地变化跳过 (Sensitive)   ← 进程退出 flush 后，仍然拦截 ✅
```

修复前此处为 `已同步 [文本] 23 字节`。**泄漏已封堵。**

> 取舍说明：该集合按内容记忆，因此若用户日后**手动**复制了完全相同的字符串，
> 也会被跳过。这是有意为之的"宁可漏同步、不可漏密码"方向；集合有 64 条上限，
> 旧条目会自然淘汰。

### 1. T2 NFC/NFD —— 根因是**我们的代码**，已修复 🔴→✅

你的问题问得很准，答案是**两者都不是"环境固有"**：

| 位置 | `café.txt` 的字节 | 形态 |
|---|---|---|
| Mac **磁盘上**（源文件） | `636166`**`c3a9`**`2e747874`（9 字节） | **NFC** |
| Mac 经 `NSPasteboard` **读回后** | `636166`**`65cc81`**`2e747874`（10 字节） | **NFD** |
| 你在 Windows 收到的 | `65cc81` | NFD |

**Mac 磁盘上是 NFC**（现代 APFS 保留 NFC，不再像 HFS+ 那样强制 NFD）。
转换发生在 **`NSURL` 经剪贴板往返**这一步——AppKit 的 URL 规范化会把文件名
转成 NFD。这是我在 `filelist.rs::read_file_paths` 里的疏漏，不是环境差异。

分步实测（用一个临时 example 打印每一步）：

```
1) Rust 直接读磁盘路径     "café.txt"       hex=636166c3a92e747874
2) 经 NSPasteboard 往返读回 "cafe\u{301}.txt" hex=63616665cc812e747874   ← 这里变了
3) meta_for_path 的 name   （取决于传入的是哪条路径）
```

**对 `id` 的实际影响**（你预判的完全正确）：

```
磁盘直取 : name="café.txt" id=e562a3c406cc636d
剪贴板往返: name="cafe´.txt" id=09f237c4633446cf
⚠️ id 不同 —— 同一个文件被当成两个，缓存必然不命中、断点续传失效
```

**修复**：在 `read_file_paths` 出口用 Foundation 自带的
`precomposedStringWithCanonicalMapping()` 归一化回 NFC（无需引入
`unicode-normalization` 依赖）。修复后：

```
磁盘直取 : name="café.txt" id=e562a3c406cc636d
剪贴板往返: name="café.txt" id=e562a3c406cc636d
id 相同 —— 缓存可命中
```

新增回归测试 `clipboard_roundtrip_preserves_nfc_filename`，已确认**移除归一化
后该测试会失败**（不是那种"删掉修复也照样通过"的假测试）。

> 关于你建议的"在 `meta_for_path` 里对文件名做 NFC 归一化后再算 id"：
> 我选择在**读取路径的出口**归一化，而不是在 `meta_for_path` 里。原因是
> 前者让 `read_file_paths` 返回的 `PathBuf` 从一开始就与磁盘一致，
> 下游（`id` 计算、文件读取、回环检测）全都受益；若只在算 id 时归一化，
> `ClipRead.file_paths` 里仍是 NFD 路径，将来别处用到还会再踩一次。
> 两种做法都能让 id 一致，这里只是取更靠上游的位置。

## 内存 +5.4MB 的成因：已查明，不是泄漏

你在 T7 里标为"待观察"的内存增长，我趁 11:38 那次断连做了对照实验。

### 结论

**内存随"处理过的最大一张图片"一次性抬升，不随时间或次数累加。**
你观察到的 +5.4MB 与图片同步吻合，不是泄漏。

### 实验数据

用同一个 release 二进制、全新配置目录、无配对的纯空闲实例做对照：

| 场景 | RSS |
|---|---|
| 刚启动（纯空闲） | 10.6 MB |
| 空闲 4 分钟后 | **9.4 MB**（不升反降） |
| 读一次 200×150 图片（120 KB） | 17.1 MB（**+6.3 MB**） |
| 再读同尺寸图 ×3 | 16.8 MB（**不再增长**） |
| 读一次 2000×1500 图片（RGBA 12 MB） | 50.6 MB |
| 再读同尺寸大图 ×2 | 50.5 MB（**仍不增长**） |
| 之后只复制小段文本 | 50.8 MB（短期不回落） |
| 再过约 10 分钟 | **16.2 MB**（分配器已归还） |

### 解读

1. **不是泄漏**：重复处理同尺寸图片时 RSS 完全持平（16.8→16.8→16.8、
   50.5→50.5）。真正的泄漏会随次数线性上升。
2. **是峰值驱动的分配器保留**：一张 200×150 的小图（原始数据仅 120 KB）就
   抬升 6.3 MB，说明开销来自解码路径的中间缓冲（TIFF 解码 + RGBA 展开 +
   `image` crate 的临时分配），而非图片本身。
3. **最终会归还**：50.8 MB 在约 10 分钟后回落到 16.2 MB。所以"不归还"是我
   一开始的错误判断——只是延迟归还，被我过早下了结论。

### 对基线数字的修正

`MACOS.md` 里记的"内存 15 MB"是**纯文本同步**场景。准确说法应为：

- 纯文本/文件同步：**~10–15 MB**
- 同步过图片后：**峰值取决于图片尺寸**，之后延迟回落

我那台跑了 4 小时的联调实例稳定在 32 MB，正是因为期间同步过一张图片
（另加 9 次文件传输），与上述规律一致。

> **建议**：这不必改代码。若要压低峰值，得改 `arboard` 的读图路径（避免
> 一次性展开整张 RGBA），属于独立优化，收益有限——图片同步本就是低频操作。
> 但**文档里的内存数字应该注明适用场景**，否则后来人看到 32 MB 会误以为
> 有泄漏，就像我们这次一样。

# 新一轮：Mac 侧缺陷排查与配对易用性改造（2026-08-07）

环境：macOS 26.5.2 / Apple Silicon / rustc 1.95.0 / 分支 `macos-platform-impl`。
起点是 118 项测试全过，结束时 **139 项全过、零编译警告**。

本轮不是按待办清单推进，而是**通读全部源码找问题**，因此下面几条此前
两侧都没记录过。

## 一、四个此前未被发现的缺陷（已修）

### 1. macOS 上设备名恒为 `unknown-host`（本文开头那个 `unknown-host` 就是它）

`main.rs` 的 `hostname_best_effort()` 只查 `COMPUTERNAME` 与 `HOSTNAME`。
Windows 上前者由系统设置，没问题；**macOS 上两个都不存在**——`HOSTNAME` 是
bash 的 shell 变量、默认不导出，zsh 根本不设它，从 launchd/Finder 启动更没有。
实测两次 `std::env::var` 都是 `NotPresent`，于是恒定退化为 `unknown-host`。

后果不只是难看：多台 Mac 配对后**彼此重名**，`list` 与托盘里分不清是哪台。
本文档开头记录的对端 Mac 名字正是 `unknown-host`，两侧都没把它当成缺陷。

改为 `device_name_best_effort()`，依次尝试：`CLIPSYNC_DEVICE_NAME`（用户显式
指定）→ `COMPUTERNAME` → `scutil --get ComputerName`（macOS 上"设置 › 通用 ›
关于本机"里的名字，可含中文）→ `hostname` 命令（去掉 `.local` 后缀）→
`HOSTNAME`。实测本机现在显示「王的MacBook Pro」。

回归测试断言 `device_name_best_effort() != "unknown-host"`，两平台都应成立。

### 2. LaunchAgent plist 未做 XML 转义（macOS）

`autostart.rs` 用 `format!` 把可执行文件路径拼进 plist。路径含 `&`（如
`~/Projects/A&B/`）会生成**语法非法的 XML**：`fs::write` 照样成功，
`is_enabled()` 也照样返回 true（它只看文件在不在），要到**下次开机**才发现
launchd 静默拒绝加载。已加 `xml_escape`。

### 3. 文件元数据与路径按文件名反查，重名时错配（两平台通用）

`arboard_backend.rs` 的读取逻辑原本先收集元数据、再按 `file_name()` 反查该
保留哪些路径。**不同目录下的同名文件**会让它失效：两条路径的文件名相同，
只要其中一个取元数据失败（文件已删/无权限），反查就会把两条都留下——于是
1 条元数据配 2 条路径。上层 `hub` 用 `zip` 配对会静默取前 1 组，结果是拿着
B 文件的标识（大小/哈希）去发送 A 文件的字节，对端**校验失败**。

改为在同一次循环里成对收集。**这条在 Windows 侧同样存在**（该文件是跨平台
代码），已随本次修复一并解决，Windows 侧无需另行改动，但值得知情。

### 4. `pending_echo` 无上限增长（跨平台核心逻辑）

`engine.rs` 的回声登记是"一写一销"，但**回声不保证兑现**：写入剪贴板后用户
立刻复制了别的内容，去抖动会把这次变化合并掉，那条哈希就再也没人消费。
`clear_pending_echo()` 虽然存在却**从未被任何地方调用**（死代码）。引擎不碰
时间（设计约束，见 `core` 的"不做 I/O"），无法按时长过期，故改为容量上限
16 + FIFO 淘汰，并删掉那个死方法。

## 二、16-bit 浮点 TIFF 图片同步失败（已修）

即 `docs/MACOS.md` 第 3 节末尾记的那个遗留缺口，本轮修掉了。

做法是**不改 arboard 的正常路径**，只在它返回错误时加一层 macOS 兜底
（`clipsync-clip/src/image_mac.rs`）：用 `NSBitmapImageRep` 取像素，让 AppKit
把它重绘到一块 8-bit RGBA 画布上，一次性归一位深、通道顺序、预乘、行距、
色彩空间。AppKit 本来就是这些图的产出方，解码不成问题。

两个实现上的坑：

- **画布不能建成非预乘**。`graphicsContextWithBitmapImageRep` 底层是
  CGBitmapContext，而 Core Graphics 只支持预乘 alpha，传
  `AlphaNonpremultiplied` 会让它返回 `nil`，且不给任何错误原因——表现为
  "画布建得出来、上下文却是空的"。改为按预乘绘制，读出时再手动去预乘。
- **尺寸不能硬编码**。Retina 屏 `backingScaleFactor = 2`，`NSImage` 的
  40×30 对应的位图是 80×60，断言要以 `pixelsWide/pixelsHigh` 为准。

实测：双实例间同步一张此类图片，153600 字节完整送达；修复前发送侧报
`读取剪贴板图片失败: ... could not be converted`。

## 三、配对易用性改造（用户反馈驱动）

原先托盘只有「显示配对码…」，**加入方只能去命令行敲 `clipsync pair <码>`**。
这是个托盘常驻的图形程序，多数用户不会开终端——等于配对只做了一半。

改动：

1. **新增 `dialog::prompt()`**：单行输入框。macOS 用 `osascript` 的
   `display dialog ... default answer`，Windows 用 WinForms 手搭（`MessageBox`
   没有输入框）。与 `show_info` 同样的注入防护：内容经 argv / 环境变量传入，
   脚本体是固定字面量。
2. **托盘新增「输入配对码…（加入对方）」**：要码 → 先试局域网自动发现 →
   找不到再问一次对方 IP（对方窗口里就列着）。同局域网的常见情形全程只需
   输一个配对码。
3. **配对结果立刻生效，不必重启**。这是配套的关键改动——原先
   `NetCtx.known` 是**启动时的快照**，从托盘配对成功后，拨号线程看不见新
   设备、入站认证也不认它，用户会看到"配对成功"然后什么都同步不了，且没有
   任何提示说该重启。改为共享的 `KnownPeers`（`Arc<Mutex<Vec<_>>>`，读时
   克隆），配对成功后同时更新设备表、地址簿、局域网信标的接纳名单，以及
   托盘上的已配对台数。

## 四、Windows 弹窗字体发虚（已修，**需 Windows 侧目视确认**）

用户反馈：「任务栏点出的配置界面，title 的字体很丝滑，但界面内文字有像素感」。

根因：`dialog.rs` 起的是 **PowerShell 子进程，而 PowerShell 默认不是 DPI
感知的**。在缩放非 100% 的屏幕上（笔记本常见 125%/150%），Windows 会把非感知
进程的窗口按低分辨率绘制再**位图拉伸**上去，文字因此发虚；而标题栏由系统
DWM 独立绘制，始终清晰——正好就是用户描述的那种割裂感。

修法（`dialog.rs` 的 `DPI_PRELUDE`）：在**创建任何窗口之前**声明 DPI 感知，
优先 PerMonitorV2（`SetProcessDpiAwarenessContext(-4)`，Win10 1703+），失败退回
`SetProcessDPIAware()`。另外输入框窗口显式设 `Segoe UI 9pt`（WinForms 默认是
Win9x 时代的 `Microsoft Sans Serif`，与现代系统格格不入）、`AutoScaleMode = Dpi`，
输入框本身用 `Consolas` 等宽字体（配对码里 `0/O`、`1/l` 更好分辨）。

**这一节我无法在 Mac 上验证，请 Windows 侧确认**：

1. 「显示配对码…」的窗口，正文字体是否已经锐利（对比修复前）；
2. 「输入配对码…」的窗口能否正常弹出、布局是否正常、回车确定 / Esc 取消是否生效；
3. 在 150% 缩放下再看一遍——这才是能区分"修好了"和"本来就没问题"的场景；
4. 用含 `"` `$` 反引号 `;` 的设备名走一遍，确认既不注入也不显示错乱。

## 五、两处健壮性加固

- **配对握手不再采信对端自报的设备 ID**（`pairing_handshake.rs`）。`DeviceId`
  就是静态公钥的指纹，本地能自己算，没有理由信别人报的。自报值与公钥不符时
  后果全是"连得上但行为诡异"的那类问题：局域网信标里的 id 是按公钥算的，与
  记录对不上会被当陌生设备丢弃（发现失效）；拨号方向由 id 字典序决定，两边
  认知不一致会双双拨号（抖动）或双双不拨（连不上）。改为按公钥派生，不一致
  时打 warn 留痕。公钥本身已由 BLAKE2s 标签认证过，据它派生的 id 因此可信。
- **`recv_body` 不再按对端声明的长度全额预分配**（`transport.rs`）。`total`
  虽已由 Noise 认证，但一个 u32 能声明 4 GB；对端实现出错时会当场把内存打爆，
  而实际数据可能一个字节都没到。改为先要 1 MiB、随实际数据增长。

## 六、测试基础设施：剪贴板测试必须串行

新增的浮点 TIFF 测试一进来，原有的两个剪贴板测试就开始随机失败——**系统
剪贴板是全局单例，而 `cargo test` 默认并行**。原有那两个测试本来也存在这个
隐患，只是碰巧没撞上。

加了 `clipboard_test_lock()`（`clipsync-clip/src/lib.rs`），所有触碰系统剪贴板的
测试都先取这把锁。锁中毒时取回内部值继续，避免一个测试失败把其余全拖成连锁
失败、掩盖真实失败点。

## 七、一条方法论教训：对照实验被自己的进程污染

值得单独记，因为它差点让我**删掉一个正确的修复**。

修完浮点 TIFF 后，我想验证"修复前确实会失败"，于是写了个小程序直接调
`arboard::get_image()` 做对照。结果它**成功**了，据此我判定"缺口在当前依赖
版本下已不存在"，把整个 `image_mac.rs`（200 行）连同接线一起删了。

删完跑测试，回归测试当场失败，报的正是 `ConversionFailure`。

真实原因：跑对照程序时，**后台还留着两个 clipsync 实例**。它们监听到剪贴板
变化，把图片同步一圈后用 arboard 的 `set_image` 写回了剪贴板——对照程序读到
的是已经被转成 8-bit 的版本，当然解得了。

两点教训：

- **做剪贴板相关的对照实验前，先确认没有本程序在跑**。这个程序的本职就是
  改写剪贴板，它在场时任何剪贴板观测都不可信。
- 那条回归测试之所以能救回来，是因为它**断言了前置条件**（先用
  `NSBitmapImageRep` 确认剪贴板里真是浮点采样，不是就跳过并说明原因）。
  没有这一步，它可能只是在验证一张普通 8-bit 图，看着是绿的却守不住任何东西

# 续：修复 Windows 侧报的配对端口故障，补齐日志与设备管理（2026-08-07 下午）

## 一、`os error 10048` —— Windows 侧截图报的那个，是必现 bug

现象：托盘点「显示配对码」，弹出「监听配对端口 47685 失败：通常每个套接字
地址只允许使用一次 (os error 10048)」。macOS 上表现为 `os error 48`，同一个
根因，与"老版本"无关——当时的代码原样存在这个问题。

**根因**：`pairing_cli::host()` 是 `loop { listener.accept() }`，**没有超时、
没有取消、除配对成功外没有任何退出路径**。命令行下没问题（`pair --host` 是
一次性进程，Ctrl+C 就结束），但从托盘发起时进程是常驻的：

> 用户点「显示配对码」，看一眼码，关掉窗口（对方还没准备好，很常见）。
> 弹窗返回后线程径直走进 accept 死循环永远卡住，`listener` 永不析构，
> 端口被占死。**再点就报 10048，只能重启程序。**

更糟的是 `spawn_pairing_announcer` 在 `bind` **之前**启动，而它的线程也是
`loop { send; sleep }`、同样停不下来——每失败一次就多泄漏一个线程，持续向
局域网广播"我在等待配对"。原注释写着"返回的句柄被丢弃时线程仍继续运行——
配对进程本身是短命的"，这个假设在托盘常驻进程里根本不成立。

**修法**：
- 非阻塞 `accept` 轮询 + **180 秒**会话超时 + 失败 **5 次**即结束（`pairing.rs`
  的注释一直声称有"短时效、错误锁定"，实际两者都不存在）；
- announcer 改为 RAII 守卫，丢弃即停；`bind` 挪到它之前，失败就不会留下线程；
- 握手本身加 30 秒读写超时，防止连上不说话的对端把会话挂死；
- 托盘侧加单例槽位：重复点击**复用当前会话、重新显示同一个配对码**，而不是
  去撞一个已占用的端口——用户重复点击时想要的本来就是"再看一眼码"。

实测：会话按时超时 → 端口释放 → 可再次发起配对。

## 组语义：为什么把"解除配对"改成了"移出设备组"

引荐建立的是**传递闭包**——A 认识 B、B 认识 C，最后三台全互联。数据模型
早已是一个**组**，但操作模型还停留在点对点的"解除与某台的配对"。两者一
冲突就出事：在 A 上解除了 C，组里的 B 还认识 C，下一轮就把它引荐回来。

上一轮为此加了 `blocked.json`（拒绝名单）去堵。名单本身随即成了新的故障
源：它不出现在任何界面里，用户点过一次"解除"之后，几个月后遇到"引荐怎么
不工作了"，完全想不到是自己造成的——实机上恰好就这么翻车了一次。

**补丁本身变成问题，通常说明该回头改模型。** 这一轮把操作对齐到数据：

| | 改前 | 改后 |
|---|---|---|
| 加入 | 显示 / 输入配对码 | 不变 |
| 移除某台 | 只清本机 + 拒绝名单 | `Removed` 广播全组，人人照办 |
| 本机离开 | 逐台解除 | 「退出设备组」，并告知对端删掉本机 |
| 隐形状态 | `blocked.json` | 无 |

`SyncMessage::Removed { device }`（协议 v3）一条消息表达两件事，区别只在
`device` 是谁：是别人 → 踢它；是发送者自己 → 我退出。收到"被移出"的那台
会清空自己的配对——否则它会带着一份别人早已作废的名单不停重连。

组内任何成员都能移出任何人，不设管理员：这些本就是同一个人的设备，消息又
只能从已配对且通过 Noise 认证的对端发来，不存在陌生人乱踢。

**已知边界**：广播时离线的成员收不到，它回来后仍认识被移出的设备，会再引荐
一次。再移出一次即可。为这种情况保留一份持久名单，等于把刚拆掉的坑重挖一遍。

## 配对码带地址，却一直要用户手敲 IP

现象：mac 与 Windows 通过 Tailscale 组网，输入配对码后连不上，再手输
`100.88.88.x` 才成。

排查先排除了网段问题——`clipsync addrs` 显示 `100.88.88.22` 已被正确归为
「覆盖网段 (100.64/10 CGNAT)」，`classify()` 的 CGNAT 判定没问题，
`best_addr_for_sharing()` 也确实优先挑覆盖网地址。

根因在 `pairing_cli.rs` 的一行：

```rust
let code_str = code.to_string();          // ← 裸的 6 位码
show_info_and_copy("ClipSync 配对", &body, &code_str);
```

进剪贴板的是**裸码**，带地址的 `ABCDEF@100.88.88.22` 只出现在弹窗**正文**里，
要用户自己选中再复制。于是对方粘过来只有码 → 没有地址 → 退回局域网组播发现
→ 覆盖网不转发组播 → 只能手敲 IP。整套"把地址并进配对码"的设计因为这一行
完全没生效，而且当时的单元测试只覆盖了 `format_pairing_string` /
`parse_pairing_input` 本身，看不出这两个函数在真实路径上没被串起来。

**这类缺口的共性**：功能各部件都对，接线错了。防它的办法是让测试断言
**真实路径上流动的那个值**，而不是各部件的输入输出。现在
`share_string_carries_an_address` 断言的就是"复制出去的那一串必须能解析出
地址"。

顺带修掉的第二个缺口：加入侧拿到带地址的码后**直连一次就放弃**，失败直接
问用户要 IP。主持方同时接着 Tailscale 和局域网时，码里带的是覆盖网地址，
而加入方可能只在局域网上——这时组播发现恰好能救回来。为此把 `join()` 拆成
`connect_host()` + `join_on()`：分两步才能区分"连不上"（值得换条路再试）
和"码不对"（再试也一样，只会白等 6 秒组播）。

## 配对码改 4 位数字，地址全自动发现

上一轮把带地址的完整串放进了主持方剪贴板，以为这样"复制粘贴一次搞定"。
**这条路从根上就是错的**：本工具要解决的正是"跨设备复制粘贴还没打通"，
在它跑通之前用剪贴板递配对码是循环依赖；也不该假设用户手边有微信之类的
传输通道。码**只能靠人念、人敲**。

于是 6 位字母数字 → **4 位数字**。

顺带把 `from_entropy` 改成拒绝采样：`b % 10` 会让 0–5 各多出 1/256 的概率
（256 不是 10 的整数倍）。30 个字符的字母表下这点偏差无所谓，1 万种组合下
不该在源头再削熵。

### 地址发现：一个探测器 + 若干候选来源

真正的分界线**不是"哪家厂商"，而是接口前缀能不能枚举**：

| 组网方式 | 接口前缀 | 能否枚举 |
|---|---|---|
| 局域网 / ZeroTier / WireGuard / Nebula | 通常 /24 | 能，照本机接口扫即可，不必认识厂商 |
| Tailscale / NetBird | **/32**，空间 100.64.0.0/10 | 不能（400 万个），只能问工具本身 |

所以 `host_probe` 让各来源只负责**产出候选地址**，再由同一个并发探测器去连
配对端口。加一种组网方式只是多一个来源，探测那一半不用动。组网工具表目前
两行（Tailscale、NetBird），且**不解析 JSON**——从输出里捞所有 CGNAT/私有段
的 IPv4 字面量。各家格式都在变，"一个 IPv4 字面量"这个特征不会变；多捞几个
无所谓（并发探测，连不上的 300ms 超时），少认一个字段名却可能让整条路失效。

### 两个只有实测才会发现的坑

**一、"端口连得上"不等于"对方在等待配对"。** 单元测试
`probing_dead_addresses_returns_quickly` 在开发机上直接失败——那台机器开着
TUN 模式代理（`utun1024` 接管了整张 IPv4 路由表），连 RFC 5737 文档专用的
`192.0.2.1` 都"连得上"。只认连接成功的话，探测会把第一个候选当成主持方，
然后握手失败，用户看到一句莫名其妙的错误。

改判据取自协议本身：主持方 accept 后**立刻**发一帧 PAKE，帧头是 4 字节大端
长度。实测确认了这个前提——连上后 23ms 收到 `00 00 00 21`（33 字节 SPAKE2
消息）。于是「前两字节为 0 且长度非零」就挡住了三类冒充者：一句话不说的代理
（读超时）、发别的协议的服务（HTTP 首字节是 `H`）、长度离谱的垃圾。

用 `peek`（MSG_PEEK）而不是 `read`：数据要留在缓冲区里给后面真正的握手用，
否则这一探就把对方的第一帧吃掉了。同样经实测确认 peek 不消费。

**二、探测会把自己的配对会话探挂。** 原先任何握手失败都计入"猜测次数"，
5 次就结束会话。探测器一上来连一批地址再断开，等于自己把自己打死。改成只有
真的发来 PAKE 且验证失败才计数——用 `anyhow` 的类型化上下文 `WrongCode`
标记，而不是匹配错误文案（文案会改，类型不会）。这同时堵掉一个骚扰：任何人
反复连一下就能让你配不上对。

### 曾考虑但没采用：路由表里的主机路由

Tailscale 会给**通信过的**对端装 /32 主机路由，`netstat -rn` 里看得到，这是
完全不认厂商的通用信号：

```
100.88.88.11   link#23   UHWIi   utun4     ← 装了 ClipSync 的 Mac mini
100.88.88.55   link#23   UHWIi   utun4     ← 装了 ClipSync 的 kpc
100.64/10      link#23   UCS     utun4     ← 整个地址空间，不可枚举
```

可惜它只覆盖"已经聊过的机器"——同样在线但没通信过的对端就没有路由，而首次
配对恰恰是"从没聊过"。为一个覆盖不到目标场景的信号，在三个平台各写一份
`netstat` / `route print` 文本解析，不划算。

### 混合拓扑不需要额外机制

A↔B 走 Tailscale、B↔C 走路由器：C 就近跟 B 配（组播，秒成），B 再把 C 引荐
给 A，全程没人输 IP。连接时地址簿对每台对端存多个候选，按
`同网段 → 覆盖网 → 公网` 排序，B↔C 自动走局域网，A↔B / A↔C 自动走 Tailscale。

## 60 秒有效期：缩短窗口买不到安全，却卡死了流程

实机上第一次配对失败了，日志说得很清楚：

```
10:16:11.041  探测 262 个候选（覆盖网 9，网段 253）
10:16:12.542  自动查找对方失败              ← 100.88.88.22 上没人应答
10:17:54.480  探测 262 个候选
10:17:54.782  发现等待配对的设备：100.88.88.22:47685   ← 302ms 命中
```

同一个地址、同样的探测，第一次没人应答，第二次 302ms 命中——**不是发现机制
的问题，是那时对方已经不在监听了**。"在 A 上点出码 → 走到 B → 打开托盘菜单
→ 敲四位数字"这一串超过了 60 秒。

那把有效期缩短到底买到了什么？**几乎什么都没有。** 挡住在线猜测的是次数
上限，不是时间窗口。为此写了一条测量（`measure_online_guessing_rate`）：

```
200 次错误猜测耗时 244ms → 818 次/秒
60 秒窗口内可猜 49078 次，而 4 位数字只有 10000 种组合
→ 没有次数上限时，单次会话被猜中的概率 100%
```

主持方的 accept 循环是串行的，所以这个速率就是在线穷举的速率。结论是两条
限制的分工完全不对称：

| | 挡住猜测的是它吗 | 放宽的代价 |
|---|---|---|
| 每会话 5 次上限 | **是，全靠它** | 拿掉 = 必破 |
| 时间窗口 | 几乎不是 | 60s → 180s，概率仍是 5/10000 |

所以：**次数上限保留（且是整个 4 位码方案的支柱），时间窗口放回 180 秒。**
"感觉次数限制影响不大"这个直觉恰好把两者搞反了——这也是为什么这里不靠感觉
下结论，而是量一遍。

### 顺带修掉的两处

**探测提速**：并发 64 → 128、greeting 超时 800ms → 400ms（主持方实测 23ms
就开口）、线程栈调到 64KiB（128 个默认栈会白占 256MiB 虚拟地址）。整轮
263 个候选从 1.5 秒降到 **929ms**，而且这是最坏情况——测量机开着 TUN 代理，
每个候选都"连得上"、都要等满 greeting。

**"没找到对方"时的提示是错的**：原先直接弹"请输入对方 IP"。可对方要是根本
没在监听，IP 填得再对也连不上——这把用户引向一条死路。改成先说最可能的原因
（"配对码 3 分钟内有效，多半是过期了"），再给两个选项：让对方重新显示、
或手动填地址。选前者会回到输入框重来一遍，正是用户实机上手动做对的那件事。

## 覆盖网那一路取到 0 个对端：路径表永远列不全

Mac mini 上第一次配对又失败了，日志一句话点破：

```
10:31:37.556  探测 254 个候选（覆盖网 0，网段 254）
                                   ^^^^^^^^^^
```

那台机器的 Tailscale **明明是通的**——配对成功后它连对端走的正是
`fd7a:115c:a1e0::…`。可组网工具那一路取到 0 个，多半是 `tailscale` 可执行
文件不在我们列的任何路径里。而两台机器又不在同一局域网（组播失败、网段扫描
扫的是本地 /24、信标报 `No route to host`），覆盖网这一路一空就彻底没辙。

顺带确认了一件事：GUI 程序从 Finder 或开机自启起来时，PATH 只有
`/usr/bin:/bin:/usr/sbin:/sbin`——Homebrew 与 .app 里的命令一个都不在里面，
所以绝对路径必须列全。开发机上实测：

```
无  /opt/homebrew/bin/tailscale          ← 原表漏了 Apple Silicon 的 Homebrew
无  /usr/local/bin/tailscale
有  /Applications/Tailscale.app/Contents/MacOS/Tailscale
```

**但光往路径表里加条目治不了本。** 路径表永远列不全：Homebrew 换前缀、装到
`~/Applications`、换个发行版、换个组网产品……所以补了一条**完全不认厂商**的
兜底 `overlay_neighborhood`：覆盖网接口的地址是 /32（正因如此
`subnet_candidates` 跳过了它），但同一个组网里的机器地址往往挨得很近——实测
该用户的 tailnet 里 5 台设备都落在 `100.88.88.0/24`。扫这个 /24 是 254 个
候选，有界、便宜、不需要任何外部命令。

这正是用户最早提的"扫本机网段最后一位的 255 个地址"，用在它真正管用的地方：
不是替代组网工具查询（那个精确得多，仍排在前面），而是在查询落空时兜住。
它**不保证**命中——Tailscale 从 100.64.0.0/10 里分配，同一个组网完全可能跨
多个 /24（该用户的 tailnet 里还有 `100.115.98.83`、`100.66.43.29`）——但把
"必然失败"变成了"大概率成功"。

候选构成变为 9（工具）+ 253（覆盖网邻域）+ 254（本地网段）≈ 516 个，
整轮实测 **1.24 秒**。日志也改成分三项报数，下次一眼能看出是哪一路空了；
一个组网工具都没找到时会明说试过多少个路径。

## 组播只从一个网卡进出：日志刷屏的背后是局域网发现从没工作过

日志里每 15 秒一条 `发送信标失败（可能无可用网络）: No route to host (os error 65)`。
功能"看起来正常"（Tailscale 通着，同步没问题），所以像是纯噪音。不是。

发送侧原本绑 `0.0.0.0` 单发一次，**出接口由路由表决定**。多网卡机器上选中的
多半不是你想要的那个。开发机实测：

```
0.0.0.0        -> ok
en0      192.168.2.177 -> ok
utun4    100.88.88.22  -> ok      （Tailscale，收下但不转发）
utun1024 198.18.0.1    -> No route to host   ← TUN 模式代理的假 IP 网卡
```

Mac mini 的默认路由走 utun，于是信标一条都发不出去——**局域网自动发现从头到
尾就没工作过**，只是被 Tailscale 那条路掩盖了。接收侧同样只在
`join_multicast_v4(.., UNSPECIFIED)` 选中的那个网卡上加入了组播组。

改成逐网卡收发（绑定各网卡源地址发送 / 在各网卡上分别加入组播组）。不用
`IP_MULTICAST_IF` 是因为标准库没暴露它，为此引入 libc 或 socket2 不值当，
而绑定源地址在 BSD/Linux 上同样能选定出接口——上面那组实测就是证据。

日志也改成只在"全都发不出去 ↔ 恢复"两个时刻各记一条，不再每轮刷。

### 改完立刻踩了自己挖的坑

同机 e2e 当场失败：逐网卡宣告之后，**同一台主机从两个网卡各来一份信标**，
而发现侧按**地址**去重，于是变成"局域网中有多台设备在等待配对"，直接报错
退出。

而我刚为这次改造写的冒烟测试**绿着放过了**——它只断言"能找到那台设备"，
没断言"算作一台"。教训：断言要覆盖**调用方真正依赖的性质**，不只是"有结果"。

改法不是把多出来的地址丢掉，而是按设备名归并成一台、保留全部地址交给
`host_probe::probe` 挨个连——一条走不通还有下一条，反倒比原来更稳。至此
组播命中的地址和主动探测出的候选走的是同一个验证器。

## 配对完要等半天：拨号线程在死等退避

实机观感"配对完还得等半天，引荐更慢"，日志量得出来：

```
10:32:38.992  已登记新配对设备 KPC        →  10:32:45.050 连上    6 秒
10:32:45.069  经 KPC 认识了 MacBook Pro   →  10:33:30.776 连上   45 秒
```

不是弹窗在挡——`register()` 在弹窗之前就调用了。是拨号线程 `thread::sleep`
死等一个退避间隔，而退避在连不上时会翻倍到上限。新设备只能干等下一轮。

改成条件变量：`KnownPeers::bump` 通知，拨号线程 `wait_for_change(version,
backoff)`。配对或引荐一登记就立刻醒，且不靠轮询——不该为了反应快就让一个
后台线程每 200 毫秒醒一次。

顺带删掉一处冗余：地址通告那个 60 秒定时块里还挂着一次无条件 `introduce_peers`，
是版本驱动引荐加进来之前的遗留。设备表没变也每分钟重发一遍，日志刷成一片
「向 X 引荐 N 台设备」，把真正的变化淹没了。

## 传大文件时让托盘图标脉冲

传输过程中图标和空闲时长得一样，用户分不清"在传"还是"卡住了"。

**信号取"最后活动时刻"而不是"进行中计数"**：计数要在收发两侧各处出口精确
配对增减，漏掉任何一条错误路径（中止、超时、连接断开、读盘失败……）就永久
泄漏，表现是图标一直闪个不停——一个只在出错后才显现、且很难查的毛病。
时间戳自己会过期：收发每个分块打一个点（`TrayStatus::note_transfer`，一次
`Instant::elapsed` 加一次原子写），1.5 秒内有活动就脉冲。1.5 秒是"分块间隙
（限速、磁盘、对端处理）盖得住、传完很快停"的折中。

**视觉上是"变淡再回来"，不是"闪没"**。图标整个消失读起来像程序崩了或连接
断了，反而制造焦虑。淡相的不透明度是在深浅两种菜单栏上逐档比出来的
（255 / 190 / 160 / 130 / 90）：

- **90** 太淡——深色栏上灰色的"未连接"几乎融进背景；
- **190** 又几乎看不出变化；
- **130** 两头都合适：一眼分得出，形状却始终饱满。

脉冲**只改透明度，不改颜色**：颜色表达连接状态、脉冲表达"在忙"，两者正交。
若脉冲顺手把颜色也改了，用户就分不清"在传文件"和"连接出问题了"。单元测试
逐像素断言了这一点（RGB 三通道不变、图形区变淡但不为 0、透明区仍透明）。

半周期 450ms，比托盘 200ms 的循环间隔长得多，免得相位被采样节奏切碎而看起来
在抖。只有 `(状态, 相位)` 变化时才重画——无脑重画等于一秒生成五张图标。

## 引荐来的设备要等整整 60 秒才变实心

```
12:42:16.877  经 KPC 认识了新设备 王的MacBook Pro
12:43:16.896  已认证并连接对端: 王的MacBook Pro
```

60.019 秒。这个数太整齐了——正是 `DIAL_RETRY_MAX`。

根因在 `learn_peers` 的两行顺序：先 `known.upsert`，后 `addrbook.add_addrs`，
中间还夹着一次磁盘写入（落盘配对记录）。而 `upsert` 会**当场唤醒**拨号线程
（上一轮刚加的条件变量），它醒来第一件事就是查地址簿——拿到一台一个地址都
没有的设备，拨不出去，这一轮记成"连不上"，退避翻倍直到上限。

**这个顺序问题本来就在**，只是从前拨号线程醒得晚、地址早就落好了，所以看不
出来。是"立刻唤醒"这个优化把它从偶发变成了必现——修一个问题时把另一个既有
的脆弱点顶到了台面上。

两层修法：

1. **顺序改对**（根因）：地址先进地址簿，再把设备加进设备表。设备表的变更
   就是"这台可以拨了"的信号，发出这个信号之前必须先让它真的可拨。
2. **退避不再把"地址还没到"当成"连不上"**（防线）：`next_backoff` 增加
   `awaiting_addrs` 与 `table_changed` 两个复位条件。就算将来又有谁把顺序
   写反，最坏也只是慢一个起始间隔（3 秒），而不是慢一分钟。

第 2 条单独成函数是为了能直接测——退避的错误表现（"断网一次之后就再也不
积极重连"）平时看不出来，只有真出事才发现。

## 托盘进度文案：两套约束，两份文案

Windows 上提示显示不全，截图里正好断在**第 64 个字符**——`NOTIFYICONDATA.szTip`
是 64 个 UTF-16 单元（63 + 结尾的 0），超出部分被系统一刀切掉，不换行也不
省略。第一次只截了文件名，不够：固定部分（`ClipSync — 接收 ` 加绝对字节数
与速率）本身就占掉五十来个字符。

注意这个上限数的是**字符数**（汉字也只算一个 UTF-16 单元），和菜单那行能占
多宽是两回事。所以提示与菜单项分开生成：

| | 约束 | 内容 |
|---|---|---|
| 菜单项 | 一行能有多宽 | `ClipSync — 接收 2026年…分.mp4 42%（3.9 / 9.3 GiB，47.3 MiB/s）` |
| 托盘提示 | ≤63 字符 | 两行，见下 |

### 提示自己换行，不交给系统

```text
接收 2026年…分.mp4 42%
3.9 / 9.3 GiB · 47.3 MiB/s
```

用户反馈"有时候换行有时候不换行"——让系统按宽度自动折行的话，速率位数一变
（`9.8 MiB/s` ↔ `123.4 MiB/s`）总长就在折行临界点上下浮动，提示一会儿一行
一会儿两行地跳。**自己定死两行**，宽度再变也只是行内长短的事。实测各种文件名
下总长稳定在 43–45 字符，两行分别约 15–19 与 26 字符，离折行阈值都很远。

前缀 `ClipSync — ` 在传输时去掉：63 的额度太紧，而鼠标正悬在它的图标上，
本来也不必自报家门。空闲时字数宽裕，前缀留着。

### 文件名固定 `前5…后5`

一开始按"剩余预算"倒推名字长度，看着更充分利用空间，实则是抖动的另一个来源
——速率位数变→预算变→名字长度变→总宽变。改成写死 5+1+5：

```
2026年度第三季度产品发布会现场录像完整版第三部分.mp4  →  2026年…分.mp4
Ubuntu-24.04.1-desktop-amd64-live-server-installer.iso  →  Ubunt…r.iso
IMG_20260807_143052_HDR_Portrait_Enhanced_Final_v3.heic  →  IMG_2….heic
```

真正有辨识度的就是开头和结尾（结尾还带着扩展名与序号），中间那段日期、参数、
哈希反而最不需要看清。定长还顺带删掉了整套"显示列宽"的判断代码（东亚全角
按区段粗判那一坨）——11 个字符最宽也就 22 列，菜单撑不爆。

日志里始终保留**完整**文件名：那是事后排查唯一的凭据，截断等于丢信息。
