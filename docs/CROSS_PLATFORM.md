## T2 文件名编码：发现 NFC/NFD 差异 ⚠️

### Windows → Mac（我发出的源端字节）

| 文件名 | UTF-8 hex |
|---|---|
| `ascii.txt` | `61736369692e747874` |
| `café.txt` | `636166`**`c3a9`**`2e747874` ← **NFC**，`é`=U+00E9 |
| `中文文件名.txt` | `e4b8ade69687e69687e4bbb6e5908d2e747874` |
| `带 空格 的文件.txt` | `e5b8a620e7a9bae6a0bc20e79a84e69687e4bbb62e747874` |
| `测试🎉emoji.txt` | `e6b58be8af95f09f8e89656d6f6a692e747874` |

发送日志：`05:36:33 已同步 [文件] 84 字节 → 1 台设备`（5 个文件）。

**需 Mac 确认**：收到的文件名 hex，特别是 `café.txt` 是 `c3a9`(NFC) 还是
`65cc81`(NFD)。

### Mac → Windows（我实际收到的字节）

| 收到的文件名 | UTF-8 hex | 与 Windows 源端对比 |
|---|---|---|
| `ascii.txt` | `61736369692e747874` | 一致 |
| `cafe´.txt` | `636166`**`65cc81`**`2e747874` | 🔴 **NFD**，与 NFC 源端**不一致** |
| `中文文件名.txt` | `e4b8ade69687e69687e4bbb6e5908d2e747874` | 一致 |
| `带 空格 的文件.txt` | `e5b8a620e7a9bae6a0bc20e79a84e69687e4bbb62e747874` | 一致 |
| `测试🎉emoji.txt` | `e6b58be8af95f09f8e89656d6f6a692e747874` | 一致 |
| `a_b_c_d.txt` | `615f625f635f642e747874` | T3，见下 |

**结论**：中文、emoji、空格全部逐字节一致；**只有带组合重音的字符出现
NFC/NFD 差异**——Windows 源端 `é` 是单码位 `c3a9`（9 字节文件名），从 Mac
收到的是 `e`+组合重音 `65cc81`（10 字节文件名）。

### 影响评估

1. **文件可正常落盘、内容无损**，肉眼看文件名也一样，所以不影响基本可用性。
2. **但会破坏跨平台缓存命中**：缓存键 `id = hash(文件名, 大小, mtime)`，
   文件名字节不同 → id 不同 → 同一个文件在两端算出两个 id，**每次都重传**，
   断点续传也无法跨方向复用。
3. 若把收到的文件再复制回去，会产生一个"看起来同名、实为不同字节"的条目。

### 待确认

我无法确定这是 **Mac 磁盘上文件名本身就是 NFD**，还是**传输路径中被转换**。
请 Mac 侧确认其源文件 `café.txt` 在磁盘上的字节：

```bash
ls | grep caf | xxd | head -2
# 或
python3 -c "import os;[print(f.encode('utf-8').hex()) for f in os.listdir('.') if 'caf' in f]"
```

- 若 Mac 磁盘上就是 `65cc81`：说明是文件创建时的规范化，属环境差异，
  可考虑在 `meta_for_path` 里对文件名做 NFC 归一化后再算 id。
- 若 Mac 磁盘上是 `c3a9`：说明我们的读取路径做了转换，需要查
  `filelist.rs` 的 macOS 实现。

**建议的修法**（待双方确认后再动）：在 `meta_for_path` 计算 `id` 时，对文件名
先做 NFC 归一化；文件名本身仍按原样传输与落盘。这样两端算出的 id 一致，
缓存命中恢复，且不改变用户看到的文件名。代价是引入一个 Unicode 规范化依赖
（如 `unicode-normalization`）。

## T5 敏感内容：发现真实泄漏缺陷，已修复 🔴→✅

### 现象

本机未安装密码管理器，故用密码管理器实际使用的标记
（`ExcludeClipboardContentFromMonitorProcessing`）模拟。**这是真实机制，
但未在真实密码管理器下验证过**，请知悉这一局限。

首次测试：密码文本被**同步了出去**，未被拦截。

### 排查

1. 查 `sensitive.rs` 的 diff → **Windows 分支未被改动**，排除本次合并引入。
2. 隔离测试（停掉守护进程排除自身干扰）→ 标记确实没设上。
3. 让设置方进程**保持存活**再测 → `06:04:52 本地变化跳过 (Sensitive)` ✅
   检测逻辑本身正常。
4. **关键观察**：该进程 8 秒后退出，随即
   `06:05:00 已同步 [文本] 23 字节` —— **同一条密码被同步了出去**。

### 根因（与平台无关，macOS 同样受影响）

1. 程序写入"密码 + 排除标记（空数据）"→ 我们正确判定敏感并跳过
2. **但 `Skip(Sensitive)` 分支不记录内容哈希**，引擎没记住这条内容
3. 该程序退出 → 系统 flush 剪贴板 → **空数据的自定义格式被丢弃，文本仍在**
4. 剪贴板序列号变化 → 监听器重读 → 看到"无标记的密码" → 判为新内容 → **广播**

即：**任何密码管理器在清理/退出/flush 后，先前受保护的密码都可能泄漏到
所有已配对设备。**

### 修复

`SyncEngine` 增加 `sensitive_hashes`（容量 64 的有界集合）：一旦判定敏感就
按内容哈希记住，**即便标记后来消失也继续跳过**。

新增两个回归测试：
- `sensitive_content_stays_blocked_after_marker_disappears`
- `sensitive_memory_is_bounded`

### 验证

实机复现原泄漏场景（设标记 → 进程退出 flush）：

```
06:31:27 本地变化跳过 (Sensitive)   ← 标记存在
06:31:33 本地变化跳过 (Sensitive)   ← 进程退出 flush 后，仍然拦截 ✅
```

修复前此处为 `已同步 [文本] 23 字节`。**泄漏已封堵。**

> 取舍说明：该集合按内容记忆，因此若用户日后**手动**复制了完全相同的字符串，
> 也会被跳过。这是有意为之的"宁可漏同步、不可漏密码"方向；集合有 64 条上限，
> 旧条目会自然淘汰。
